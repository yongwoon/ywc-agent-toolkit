## Purpose

Close the two verified gaps between the external SDLC v1.1 workflow and the
Codex bundle without duplicating skills that the bundle already covers.

The result is a direct implementation entry point for one approved spec or
ticket, and a review range that is anchored at the merge-base of a caller's
fixed point. Existing brainstorming, planning, specification, task generation,
research, TDD, review, and Wayfinder roles remain intact.

## Scope

- Add `codex/skills/ywc-implement/` for one approved spec or ticket.
- Amend `codex/skills/ywc-impl-review/` so a fixed-point review uses
  `git merge-base <fixed-point> HEAD` and reviews that merge-base through HEAD.
- Update only Codex bundle metadata, localized README files, evaluations, and
  generated marketplace output required by those two changes.

## Out of Scope

- Changes under `claude-code/`, `codex/agents/`, installation scripts, or
  repository CI behavior.
- Copying external `implement`, `research`, `prototype`, or `code-review`
  skills verbatim.
- Adding `ywc-prototype`: no repository request demonstrates repeated use yet.
  Reconsider it when a real state-model or UI-direction decision needs a
  disposable, runnable artifact.
- Altering `ywc-code-gen`, `ywc-sequential-executor`, or
  `ywc-parallel-executor` ownership beyond their documented handoffs.

## Functional Requirements

### FR-1: Add `ywc-implement`

> ⚠️ SUPERSEDED by Iteration 1 — see §Iteration 1 Amendments.

Create the skill as the small, direct implementation lane:

1. Accept exactly one approved spec path or ticket reference; reject a vague
   request with a route to `ywc-brainstorm` or `ywc-plan`.
2. Read project instructions, the approved input, and only relevant existing
   implementation/tests before editing.
3. Reuse the existing pattern where possible; do not introduce a parallel
   generator, executor, or custom agent.
4. For behavior changes, run the `ywc-tdd-ritual` RED → GREEN discipline at
   the selected seam. Run focused checks while editing and the project-wide
   configured checks once before completion.
5. Run `ywc-impl-review` against the change range, resolve only confirmed
   Critical/High issues within one bounded correction cycle, then commit using
   repository convention.
6. Return changed files, commands with exit status, review status, commit SHA,
   and any unresolved concern.

Keep detailed command discovery and output examples out of the trigger
description. Do not add scripts unless a deterministic operation cannot be
expressed by existing Git and project commands.

### FR-2: Make review fixed points merge-base aware

> ⚠️ SUPERSEDED by Iteration 1 — see §Iteration 1 Amendments.

Extend `ywc-impl-review` arguments with a clear fixed-point mode, preferably
`--base <ref>`, while preserving `--git-range A..B`.

For `--base <ref>`:

1. Resolve the ref using `git rev-parse --verify`.
2. Calculate `git merge-base <ref> HEAD`.
3. Require a non-empty `git diff --name-only <merge-base>...HEAD` result.
4. Use the same three-dot diff to collect the patch/final contents sent to
   every Phase 1 worker.
5. Print the supplied ref and resolved merge-base in the report header so the
   review boundary is auditable.

Do not replace `--working-tree`, `--code`, or explicit `--git-range` behavior.

### FR-3: Update connected skill metadata and documentation minimally

Update `ywc-code-gen` and `ywc-sequential-executor` only if their descriptions
or integration text need the new direct lane to prevent misrouting. Regenerate
the new skill's UI metadata from its final SKILL.md. Add only Tier 1 README
files unless the translation workflow determines Tier 2 files are maintained
for this new skill.

### Amended Direct-Implementation Contract

> ⚠️ SUPERSEDED by Iteration 2 — see §Iteration 2 Amendments.

`ywc-implement` accepts exactly one of these inputs:

- `--spec <repo-relative-path>`: an existing approved specification.
- `--ticket <reference>`: a readable ticket reference that resolves before
  editing to a local, immutable snapshot containing its acceptance criteria and
  approval evidence. An inaccessible, ambiguous, or unapproved ticket returns
  `NEEDS_CONTEXT`.

Before editing, require a clean working tree, record `git rev-parse HEAD` as
the baseline, and work on a feature branch. If the caller is on a long-lived
branch, create or request a feature branch before changing files; never commit
user-owned changes. Run the existing-pattern inspection and TDD/focused checks
as specified in FR-1.

Run the full configured verification before review. Use
`ywc-impl-review --spec <resolved-spec> --working-tree` when the implementation
has no commits since the recorded baseline; after TDD checkpoint commits, use
`--git-range <baseline>..HEAD`. The direct lane does not use `--base` for its
own pre-commit review.

Review routing is mandatory: `BLOCKED` or `NEEDS_CONTEXT` stops without a
commit. For confirmed Critical or High findings, make at most one correction
cycle, rerun every affected check plus the configured full verification, then
re-review the same boundary. Unresolved Critical/High findings return
`DONE_WITH_CONCERNS` and do not commit unless the user explicitly directs an
override. Commit only after a clean review result, using the repository's
conventional format; never create a PR, force-push, or amend a published commit
without explicit user request.

### Amended `ywc-impl-review --base` Contract

`--base <ref>` is a fourth, mutually exclusive review target. Require exactly
one of `--base`, `--git-range`, `--code`, or `--working-tree`; reject mixed or
missing target modes with `NEEDS_CONTEXT` before reading review files. Resolve
`<ref>` as a commit with `git rev-parse --verify <ref>^{commit}`, compute
`git merge-base <ref> HEAD`, and return `NEEDS_CONTEXT` when either operation
fails or `git diff --name-only <merge-base>...HEAD` is empty.

For a valid base mode, use `<merge-base>...HEAD` consistently for the changed
file list and patch sent to every Phase 1 worker, and provide each worker the
corresponding final file contents. The report header prints both the supplied
ref and resolved merge-base. `--git-range A..B` remains an explicit,
two-endpoint comparison; `--code` and `--working-tree` retain their current
semantics.

## Iteration 2 Amendments

### Failed Requirements

- The TDD checkpoint path allowed an uncommitted correction that the required
  `--git-range <baseline>..HEAD` re-review could not see.
- The direct lane did not define an approval marker for `--spec` or the local

### Amended Review and Approval Protocol

`--spec <repo-relative-path>` is eligible only when the document is readable,
contains explicit approval evidence (for example `Status: Ready for
implementation` or `Approved: yes`), and contains acceptance criteria. Missing
or contradictory evidence returns `NEEDS_CONTEXT`. A resolved `--ticket` must
produce the same repository-readable snapshot; that snapshot path is the
`--spec` argument passed to `ywc-impl-review`.

TDD RED/GREEN/REFACTOR checkpoints are permitted as local, unpublished commits.
They are an exception to the pre-review commit prohibition, not delivery: no
push, merge, PR, or final success status is allowed before the clean review
gate. For a correction after a range review, first rerun affected checks, make
one local unpublished correction checkpoint, rerun the configured full
verification, then re-review `<baseline>..HEAD`; this range now includes both
the original TDD commits and the correction. For a working-tree review, keep
the correction uncommitted and re-review `--working-tree` after the same
verification. A re-review that still has Critical/High findings ends
`DONE_WITH_CONCERNS` without delivery unless the user explicitly overrides.

### Updated Acceptance Evidence

- **AC2 amendment:** The eval covers both review paths: an uncommitted direct
  change uses `--working-tree`, while TDD checkpoints and a bounded correction
  use the recorded `<baseline>..HEAD` range; neither path may push, merge,
  create a PR, or report final success before a clean review.
- **AC6 amendment:** The direct-lane eval rejects a spec lacking explicit
  approval evidence or acceptance criteria, and verifies that a resolved ticket
  supplies the local spec path used by `ywc-impl-review`.
