## Purpose

`ywc-parallel-executor`'s wave-boundary mutation gate (Step 4e.5, "Hardener") runs **after** Step 4e has already merged every wave task into the base branch and stamped both the `task-merged` and `wave-complete` checkpoints. An `enforced` Quality Gate Contract returning `BLOCKED` at 4e.5 therefore cannot prevent anything — the changes are already delivered. Under `--per-task-pr` the delivery is a merged-and-deleted PR against the remote base, undoable only by a revert PR.

This is not an accident to be quietly patched. The parent spec's FR-4 placed 4e.5 there **deliberately**, for a stated and still-valid reason: *"runs once against the wave's merged diff, since cross-task interaction gaps only surface post-merge."* This spec keeps that property — Hardener must still see a merged wave diff — while moving the merge target off the delivery branch. It therefore **supersedes the parent spec's placement decision** and must be read alongside it.

The sibling skill `ywc-sequential-executor` already has the correct ordering (Cleaner at Step 3.5 and Hardener at Step 3.6, both before Step 5 Delivery), so `ywc-parallel-executor` is the divergent one, and the fix generalizes prior art that already exists in this repository rather than inventing a mechanism.

## Functional Requirements

### FR-1: Wave integration branch for the three isolable modes

For `--local-merge`, `--draft`, and `--aggregate-pr` — settled as the isolated set; no consumer dependency on per-task remote visibility mid-wave was found, so `--per-task-pr` remains the only carve-out — Step 4e creates `wave-int/<N>` from the current base at wave start **only when the wave contains at least one task with a declared Quality Gate Contract** (FR-11's OR-based routing rule; AC12). This check is performed once, during the Pre-flight computation FR-5 specifies — Step 4e does not re-derive per-task contract state at wave start; it creates `wave-int/<N>` if and only if that wave's `integration_branch` value is already non-`None` in `.ywc-run-state.json`. A wave where every task is contract-less skips `wave-int/<N>` entirely and delivers direct to base exactly as today.

When `wave-int/<N>` is created, it is pushed to origin immediately, before any task's `ywc-finish-branch` call runs against it — generalizing `ywc-sequential-executor/references/aggregate-pr.md:30,34-35`'s `WORK_BRANCH` push-at-creation sequence from a run-level branch to a wave-level one. This is required: `ywc-finish-branch/SKILL.md:218-226`'s `local-merge` sequence runs `git pull origin <base-branch>` unconditionally per task, which fails with `fatal: couldn't find remote ref` against a local-only branch. No change to `ywc-finish-branch` itself is needed once the remote ref exists.

The mechanism otherwise is the existing `--base-branch` redirection already used by `ywc-sequential-executor`'s `--aggregate-pr` (`--base-branch work/<name>`) — each mode-mapping row simply passes `--base-branch wave-int/<N>` instead of the real base. The per-task `task-merged` checkpoint keeps its current position and its `pending → merged` transition; only its meaning changes, and that change is recorded in `checkpoint-resume.md` (FR-6) rather than in the state schema.

**Idempotent creation (added Iteration 3, Critical #1).** Branch-creation is not "always branch `wave-int/<N>` from base": before creating it, check whether `wave-int/<N>` already exists (locally or on `origin`). If it exists, reuse it — merge the remaining `pending` tasks onto it exactly as if the run had never stopped. Only branch from base when it does not exist. This is what makes a partial-merge interruption (some but not all wave tasks already merged onto `wave-int/<N>` when the run stopped) safe to resume: without this check, a naive re-creation would silently discard every task merged before the interruption. See `checkpoint-resume.md`'s extended resume table (FR-6) for the full partial-merge resume case.

**No new concurrency mechanism needed (added Iteration 3, Suggestion #1).** Step 4e's per-task delivery loop is already sequential — "For each task in the wave sequentially (topological order within the wave)" (`SKILL.md:268`) — so merging multiple tasks onto the shared `wave-int/<N>` target introduces no new race condition; delivery was single-threaded against base today and stays single-threaded against `wave-int/<N>` under this spec. No locking or mutex is required around the merge step.

### FR-2: Promotion step, gated on Hardener

After Step 4e.5's Hardener returns for a wave that created `wave-int/<N>` (FR-1), promote it into the base branch **only** when the gate did not block. (A fully contract-less wave never created `wave-int/<N>` and is unaffected by this FR — it already delivered direct to base at Step 4e.) Promotion is a fast-forward of base to the integration branch, followed by the mode's existing push behavior — immediate push for `--local-merge`, deferred for `--draft` / `--aggregate-pr`. The `wave-complete` checkpoint is stamped **after** a successful promotion, making it the promotion checkpoint; its existing "refuses while any task is pending" guard in `update-state.py:162-163` is retained unchanged as the promotion precondition. On a blocking gate result, base is left untouched, `wave-complete` is not stamped, the integration branch is preserved, and Step 4g cleanup is skipped for every task in the wave — matching the existing preserved-failure convention.

Step 4e's existing sentence "Delivery into the base branch is required for **every** mode because downstream waves branch from it" (`SKILL.md:264`) is **retained**, with one added clause explaining that post-promotion base content is identical to the integration branch, so wave N+1 still branches from base and the invariant holds. Lineage changes within a wave only, never across waves. The sentence must additionally be reworded so that "the base branch" is not misread as the *per-task merge target*, which is now `wave-int/<N>` for the three isolated modes.

**Postcondition (added Iteration 3, Suggestion #2).** After promotion's fast-forward (`git checkout <base>; git merge --ff-only wave-int/<N>; git push` for `--local-merge`, or the deferred-push equivalent), the main checkout's `HEAD` is left on `<base-branch>` — this is the postcondition the next wave's Step 4a (worktree creation) already assumes when it branches from base. State this explicitly in the new promotion reference (FR-9) so an implementer does not need to infer it from the command sequence.

### FR-3: The carve-out rule and the `--per-task-pr` advisory cap

State the rule, then its consequence. The rule: *an isolation branch can only protect state whose point-of-no-return sits after the gate.* The consequence: `--per-task-pr` reaches its point-of-no-return at `gh pr merge --delete-branch`, once per task, **inside** the wave, so no branch topology can move it behind the wave boundary — this is a timing property, not a topology one. Therefore under `--per-task-pr` the wave-boundary Hardener is reporting-only and may not return `BLOCKED` even under an `enforced` contract; blocking authority for that mode lives entirely at Step 4c.5, which already runs per-task before PR creation. The skill must say *why* rather than listing the exclusion.

### FR-4: Promotion-conflict behavior (advisor Concern 2)

Specify explicitly what happens when the base branch advanced during the wave and the fast-forward promotion fails. Silently degrading to a merge is forbidden: the merge can introduce conflicts *after* Hardener already passed against the un-merged integration branch, which reintroduces the exact class of defect this spec removes. The required behavior is to merge base **into** `wave-int/<N>` (never rebase, per `references/pr-conflict-resolution.md`), then **re-run Hardener** against the merged result before retrying promotion; a real textual conflict on that merge marks the wave `BLOCKED`, preserves the integration branch and every task worktree, and surfaces the conflicting files to the user without auto-resolution or force-push.

**Two-counter attempt bound (added Iteration 3, resolves advisor escalation on unbounded retry).** This re-run is a second wave-boundary Hardener dispatch for the same wave and must not share a naive single counter with the first dispatch — the two failure modes it can hit are different and need separate bounds:

- **Mutation Loop Cap is scoped per Hardener *dispatch*, not per wave.** Each dispatch — the initial wave-boundary run, and each post-merge re-run — gets its own fresh 3 approved attempts (`quality-gates.md` §"Mutation Loop Cap"), because a base-merge produces genuinely new content the prior dispatch never measured; giving the re-run 0 attempts left would silently downgrade "re-run Hardener" to inspection-only.
- **Live-lock (base advancing indefinitely, clean merges each time) is bounded by a separate per-wave counter, `promotion_retry_count`, capped at 2.** Exceeding it marks the wave `BLOCKED` with reason `promotion-churn` — distinct from the textual-conflict `BLOCKED` reason above — preserves the integration branch and every task worktree, and surfaces the base-churn condition to the user without auto-resolution or force-push.
- Worst case is therefore explicit and bounded: 3 dispatches × 3 mutation attempts = 9 total Hardener attempts per wave, then `BLOCKED`.

`promotion_retry_count` is delivery/topology retry-accounting state, not gate state (parent spec FR-4) — it is never written as a `gate_state` value.

### FR-5: `update-state.py` — one new field, both copies

Add `integration_branch` to each wave entry in `cmd_init_parallel`, seeded via `setdefault` exactly like the existing `status` / `merged` / `pending` keys so an in-flight state file written by the previous version stays loadable. The wave number is already available inside the `for wave in waves` loop, so the seed value is the computed branch name when the wave both uses an isolated mode and contains ≥1 contract-bearing task (FR-1, FR-11), and `None` otherwise — for a `--per-task-pr` wave, or for a fully contract-less wave under an isolated mode — the field is written once at init and never mutated by `task-merged` or `wave-complete`, which keep their existing signatures. No new subcommand is added. Apply the identical edit to `claude-code/skills/scripts/update-state.py` and `codex/skills/scripts/update-state.py` (byte-identical today but for one docstring line), then let `.githooks/pre-commit` regenerate the `plugins/` mirror. Under no circumstance is a `gate_state` value written into `.ywc-run-state.json` — the parent spec forbids it, and `integration_branch` is delivery topology, not gate state.

**Data source for the contract-bearing check.** `cmd_init_parallel`'s only input is the `--waves` JSON array (`{"wave":N,"tasks":[...]}`) — task names, nothing else. It has no independent access to any task's declared `spec` → `quality_gate_contract` field (`references/quality-gates.md` §1, §7), so the "contains ≥1 contract-bearing task" condition above cannot be evaluated inside `cmd_init_parallel` as written. The Pre-flight sequence must compute this **before** calling `init-parallel` and pass the result through: for each wave, read every member task's declared `quality_gate_contract` field from its task-directory spec/README, and OR across the wave's tasks — the wave is contract-bearing if any task's field differs from the `N/A — no quality gate contract` sentinel (`references/quality-gates.md` §7), and contract-less only if every task's field equals that sentinel. Extend the `--waves` JSON schema with this per-wave boolean, e.g. `{"wave":1,"tasks":["t-a","t-b"],"has_contract":true}`, and `cmd_init_parallel` reads `wave.get("has_contract", False)` — the `False` default preserves today's behavior for any caller that omits the field, matching the `setdefault` backward-compatibility discipline used elsewhere in this FR. This is a Pre-flight scan added ahead of the existing `init-parallel` call, not a new subcommand; `cmd_init_parallel`'s signature and call shape are otherwise unchanged.

**Malformed / missing field handling (added Iteration 3, Critical-adjacent Completeness gap).** The Pre-flight scan above is defined only for the clean case (field present and equal, or not equal, to the exact `N/A` sentinel). Three additional cases must not silently resolve to `has_contract: false`: (1) a task's `quality_gate_contract` field is missing entirely rather than carrying the sentinel string, (2) the field is present but malformed/unparseable, (3) a task directory named in `--waves` does not yet exist at Pre-flight scan time. Each of these three cases **stops Pre-flight with `NEEDS_CONTEXT`**, naming the offending task and the missing/malformed field — never a silent `false` default. Silently downgrading a task with an unreadable contract field to contract-less is exactly the routing regression FR-11 warns against (it would route a possibly contract-bearing wave direct to base). Only an explicit, correctly-formatted `N/A — no quality gate contract` sentinel is treated as `false`.

**Additional state fields introduced elsewhere (cross-reference, added Iteration 3).** This FR seeds `integration_branch` only. Two further fields — `hardener_verdict` (FR-6) and `promotion_retry_count` (FR-4) — are added to the same per-wave state entry via the identical `setdefault` backward-compatibility discipline described above, but are written by the promotion/Hardener call sites rather than by `cmd_init_parallel`'s seeding path. AC7 covers all three fields together.

### FR-6: `checkpoint-resume.md` — the un-promoted-wave resume case

For a wave that created `wave-int/<N>` (FR-1) — amend the checkpoint-event table so the Step 4e row reads as a merge onto the integration branch, and add the promotion row for `wave-complete`. Add the resume rule the new topology makes possible: such a wave whose `pending` is empty but whose `status` is not `completed` is unambiguously "merged onto the integration branch, not yet promoted." A fully contract-less wave (no `wave-int/<N>` ever created) keeps today's resume behavior unchanged. Record that this is a strict improvement for isolated waves: today that same interruption is indistinguishable from a completed wave.

**Partial-merge resume (added Iteration 3, Critical #1).** The case above covers only the *fully*-merged-not-promoted wave. A wave interrupted with some but not all tasks merged onto `wave-int/<N>` (`pending` non-empty, `wave-int/<N>` already exists) resumes by reusing the existing branch and merging the remaining `pending` tasks onto it — per FR-1's idempotent-creation rule, Step 4e never re-branches `wave-int/<N>` from base when it already exists. Only once `pending` is empty does the wave enter the fully-merged-not-promoted state below.

**Disambiguating bare interruption from a deliberate Hardener `BLOCKED` (added Iteration 3, resolves advisor escalation).** The fully-merged-not-promoted state (`pending` empty, `status != completed`) is reached identically whether the run merely crashed before Hardener ran, or whether Hardener already ran and explicitly returned `BLOCKED` (an unresolved real cross-task defect). These two situations must not be treated the same way on resume. Add a `hardener_verdict` field (`absent | PASS | BLOCKED`), written at Hardener exit **before** promotion is attempted:

- `hardener_verdict` **absent or `PASS`** — the common transient case (interrupted before Hardener ran, or passed but died before promotion). Resume **auto-retries** Hardener + promotion with no prompt; Hardener is a measurement gate, so re-running against unchanged input is a safe no-op.
- `hardener_verdict` **`BLOCKED`** — a deliberate, unresolved gate failure. Resume **stops and prints the recorded blocking findings**, then requires explicit user confirmation before re-running Hardener — matching the human-in-the-loop convention already used for every other `BLOCKED` condition in this skill (merge conflict, circular dependency, base-refresh conflict). Idempotency makes the re-run *safe*, not *informative*; silently re-deriving an unresolved BLOCKED days later would train the user to ignore the gate.

`hardener_verdict` is written once per Hardener dispatch and is reset to `absent` when a new dispatch begins (e.g., the FR-4 post-merge re-run); it never carries a severity assignment, so it is not a `gate_state` value under the parent spec's constraint.

### FR-11: Contract-absent no-op preservation, and the OR-based mixed-wave routing rule

Every section this spec creates or amends that references a quality gate — the Step 4e delivery routing (FR-1), the promotion step (FR-2), the carve-out statement (FR-3), the codex equivalents (FR-7), and the two `quality-gates.md` additions (FR-8) — must restate the `N/A — no quality gate contract` skip behavior, or point to §7 of `quality-gates.md`, rather than assuming a contract exists. This is the no-block invariant the parent spec established and the single most likely regression of this change: routing a fully contract-less wave onto an integration branch it does not need would impose the new topology's cost on the majority of projects that never adopted quality gates.

**Resolved routing rule** (Amendment Log Iteration 1): a wave where **every** task is contract-less delivers direct to base, unchanged from today, and never creates `wave-int/<N>`. A wave where **any** task declares a Quality Gate Contract routes the **entire** wave — including its contract-less tasks — through `wave-int/<N>`, because Hardener's cross-task-interaction check (FR-2, Existing Constraints Touched `SKILL.md:351`) requires the full merged wave diff and cannot isolate one task's contribution from its wave-mates. The routing decision is evaluated once per wave (OR across its tasks' contract states), never per-task — and that evaluation happens once, during the Pre-flight scan FR-5 specifies, before any wave executes, never re-computed at Step 4e.

## Edge Cases

- **Wave with no quality gate contract**: resolved (Amendment Log Iteration 1) — a fully contract-less wave (every task `N/A`) delivers direct to base, unchanged from today, and never creates `wave-int/<N>`; no integration branch is needed and the gate is a clean no-op. A wave with at least one contract-bearing task routes entirely through `wave-int/<N>` even though some of its tasks are contract-less (FR-1, FR-11, AC12).
- **Base advanced during the wave (advisor Concern 2)**: fast-forward fails; FR-4 governs — merge base into the integration branch, re-run Hardener, retry promotion; real conflict → wave `BLOCKED`, nothing force-pushed.
- **Hardener dispatch failure**: unchanged from today — `DONE_WITH_CONCERNS`, never `BLOCKED` (`SKILL.md:351`). A dispatch failure must therefore still allow promotion, or the new topology would convert a documented non-blocking condition into a blocking one. This must be stated explicitly.
- **Interruption after task merges but before promotion**: the new unambiguous resume state (FR-6). If `pending` is non-empty, `wave-int/<N>` already exists and resume reuses it, merging the remaining tasks (FR-1's idempotent-creation rule). Once `pending` is empty, resume branches on `hardener_verdict`: absent/`PASS` auto-retries Hardener and promotion; `BLOCKED` requires explicit user confirmation before re-running (FR-6).
- **Interruption during promotion itself**: the fast-forward either landed or did not; `wave-complete` is stamped only after it lands, so resume re-attempts an already-satisfied fast-forward, which is a no-op. This ordering must be preserved exactly — stamping before the promotion would recreate today's ambiguity.
- **Single-task wave**: the integration branch adds one branch and one fast-forward for no isolation benefit that a per-task branch does not already provide. Acceptable overhead, but the spec should not special-case it — a linear chain is already routed away to `ywc-sequential-executor` by the Step 2 linear-chain guard.
- **`--aggregate-pr` / `--draft` end-of-run reset**: `aggregate-pr.md` runs `git reset --hard origin/<base>` on the local base after carving the aggregate branch. If any wave is un-promoted at that point, the reset must not be the step that discards it — the carve must happen after the last wave's promotion, or the run must refuse to carve while an un-promoted integration branch exists.
- **A project whose CI or tooling watches the base branch for per-task commits**: this was advisor Concern 1. Resolved (Amendment Log Iteration 1) — the change converts per-task pushes into one wave-granular push under `--local-merge`, and no such consumer dependency blocks it; `--local-merge` proceeds with wave-int isolation per FR-1.
