# Port: Subagent Async Monitoring Contract (develop-with-llm PR #229/#230)

## Purpose

`develop-with-llm` PR #229 and PR #230 introduced a shared contract — the **Subagent Async Monitoring Contract** — that prevents an orchestrating skill from losing track of concurrently-dispatched subagents when their completion notifications arrive asynchronously. It was root-caused from a real incident in the `marketing-ecosystem` project where two concurrently-dispatched subagents' completion notifications were mixed up and a completed task was mistaken for still-pending for ~40 minutes.

This repository (`ywc-agent-toolkit`) has the identical class of exposure and does not yet have the contract:

- `claude-code/skills/ywc-parallel-executor/SKILL.md` Step 4b dispatches one subagent per task **in parallel**, per wave, via the `Agent` tool (`SKILL.md:207`) — the exact pattern that caused the source incident.
- `claude-code/skills/ywc-impl-review/SKILL.md` Phase 1 dispatches **5 concurrent subagents** (Architecture/Design/Devex/Security/QA), and Step 4.5 can dispatch **up to 20 concurrent Sonnet verifier subagents** (`SKILL.md:112` dispatch cap) — the highest-concurrency fan-out in this toolkit, and the most exposed to the exact race the source incident describes.
- `claude-code/skills/ywc-sequential-executor/SKILL.md` is sequential by default, but its Advisor Escalation Policy (bounded Opus dispatch) and `--review` auto-invocation of `ywc-impl-review` (which internally fans out per above) mean an ad-hoc, unplanned background dispatch mid-task/mid-range carries the same risk.

## Scope

Port the contract into **claude-code skills only** (`claude-code/skills/`). `codex/skills/` is explicitly out of scope for this pass — develop-with-llm's own codex port (Phase yw-000007 in PR #229's history) is a separate, already-proven adaptation; this repository's `codex/skills/` equivalent is deferred to a follow-up per its own note in `claude-code/skills/CLAUDE.md` ("Codex-skill: Maintained Independently").

The prose is **not** copied verbatim from develop-with-llm — it is rewritten to this repository's conventions:
- A single new top-level reference file under `claude-code/skills/references/`, registered in `claude-code/skills/CLAUDE.md` the same way `pr-bot-polling.md` and `pr-conflict-resolution.md` are registered (mirrored section format, explicit "Action required" directive convention).
- `ywc-parallel-executor`'s Status Routing is an **inline table inside `SKILL.md`** in this repo (there is no separate `references/status-routing.md` file here, unlike develop-with-llm) — the new row is added to that inline table, not a new file.

Any addition here must be paired with an equal-or-greater trim elsewhere in the same file to stay under the cap — mirroring the exact regression-and-fix pattern that occurred in the source PR #230 itself (`fix: trim ywc-sequential-executor body under 500-line S4 threshold`).

## Functional Requirements

- FR1 — New reference file `claude-code/skills/references/subagent-async-monitoring.md` with the four required sections (AC5). Content basis, adapted (not copied) from develop-with-llm PR #229/#230:
  - **Unique Dispatch Labeling**: every subagent dispatched as part of a concurrent batch (a wave in `ywc-parallel-executor`, the 5-way Phase 1 fan-out or 20-way Step 4.5 fan-out in `ywc-impl-review`) must be given a name that deterministically maps back to what it was dispatched for (task name, or `<aspect>-<verifier-index>` for impl-review's verifier fan-out) — never a generic/reused label across a batch.
  - **Full-Roster Reconciliation**: before treating a batch as complete, the orchestrator must reconcile the full expected roster (the set of names it dispatched) against the set of names it has received a terminal status for — via the runtime's own agent-listing capability where one exists, or otherwise the batch's own tracked state (a checklist of dispatched names ticked off as each terminal status arrives) — rather than inferring completion from notification arrival order or count alone. This is the direct fix for the source incident (two notifications arriving out of order were treated as "the wrong one still pending"). Reconciliation must be safe to invoke repeatedly against the same state — a duplicate terminal-status notification for an already-reconciled name is a no-op, never treated as a second batch member.
  - **Mandatory Fallback Wakeup**: after dispatching a batch of 2+ concurrent subagents, the orchestrator sets an explicit bounded wait/check point — the runtime's own scheduled-recheck capability where one exists, or otherwise a manual "check back after N seconds" discipline the orchestrator holds itself to — rather than passively waiting on notifications alone. Threshold table (adapted from develop-with-llm PR #230's 480s/900s hardening, expressed in this repo's own terms):

    | Batch size | Soft-check interval | Hard escalation threshold |
    |---|---|---|
    | 2–4 concurrent subagents | 480s | 900s |
    | 5+ concurrent subagents (e.g. impl-review Phase 1, Step 4.5) | 300s | 600s |

    Cancel the fallback the moment full-roster reconciliation confirms every dispatched name has a terminal status — never let a stale fallback fire after the batch is already known complete (mirrors PR #230's "fallback wakeup cancellation rule").
  - **Bounded Escalation on Stall**: if the hard escalation threshold is reached and full-roster reconciliation still shows one or more names without a terminal status, treat it as the batch-level equivalent of `BLOCKED` per `../references/subagent-status-actions.md` — do not keep waiting indefinitely, and do not silently re-dispatch. Surface which named subagent(s) are unaccounted for.
  - **Known Limitations**: this contract mitigates but does not eliminate notification races; a subagent whose process exits without ever emitting a terminal status is indistinguishable from one that is merely slow until the hard threshold fires.

## Edge Cases

- **`ywc-sequential-executor` in single-task (non-range) mode**: the contract's batch-size thresholds (FR1) are keyed to 2+ concurrent dispatches; a single-task invocation with no `--review` fan-out never triggers the fallback-wakeup machinery at all — the new Rationalization Defense row (FR4) and Advisor Escalation Policy cross-reference (FR5) apply only when a concurrent dispatch is actually considered (e.g., mid-task ad-hoc forking, or the `--review` flag's downstream `ywc-impl-review` fan-out).
- **`ywc-impl-review` with `--no-advisor`**: Phase 1's 5-way fan-out and Step 4.5's verifier fan-out still run regardless of `--no-advisor` (that flag only skips Phase 2). The async monitoring citations in FR7 apply to both regardless of the flag.
- **A wave of exactly 1 task in `ywc-parallel-executor`**: the existing Linear-chain guard (`SKILL.md:168`) already routes single-task-per-wave inputs to `ywc-sequential-executor` before Step 4 is reached, so the `4b-monitor` gate's "2+ concurrent" precondition is never violated in practice — no additional guard is needed in Step 4b itself.
